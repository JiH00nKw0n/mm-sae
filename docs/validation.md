# 실행 확인 기록

**2026년 9월 14일, 텍스트 토큰을 unknown token으로 치환하는 방식으로 실제 COCO 이미지 6장과 캡션 30개를 CPU에서 검사했다.** 기존 소규모 실행에서 저장한 이미지·텍스트 SAE를 불러왔으며 새 학습은 수행하지 않았다. 학습 전후 가중치 파일의 지문이 같았다. 데이터 준비부터 보고서 생성까지 아홉 단계가 종료 상태 0으로 끝났다. 결과는 `/Users/jihoonkwon/Desktop/projects/research/MM-SAE/mm-sae/runs/unk-mask-smoke-real`에 저장했다.

텍스트 가림 입력은 50개, 이미지 가림 입력은 44개를 계산했다. 같은 캡션이나 이미지에서 다른 개념을 가린 경우는 별도 입력으로 센다. 이 실행은 작은 자료에서 처리 경로를 확인한 것이며, 전체 자료의 대표 품질이나 연결 회복 성능을 검증한 결과는 아니다.

별도로 고정된 실제 CLIP에서 캡션 16개의 객체 표현 28개를 가렸다. `unk_token_id`는 49407이며 `eos_token_id`와 같았다. 가리지 않는 위치의 토큰 번호와 원래 문장 종료 위치가 유지되는지 확인했다. 아무 토큰도 가리지 않을 때 기존 `get_text_features` 결과와 차이가 0이었고, 28개 가림 입력은 모두 원본과 다른 문장 벡터를 냈다. 주석의 의미가 정확한지와 별개로 치환 연산을 검사한 결과다. 기록은 `/Users/jihoonkwon/Desktop/projects/research/MM-SAE/mm-sae/runs/unk-mask-token-audit.json`에 있다.

Ruff 검사와 형식 검사, Pyright, 단위 검사 30개를 통과했다. 단위 검사에는 여러 토큰으로 나뉜 단어, 반복 표현, 길이 제한으로 잘린 표현, 가릴 토큰에 다른 표현이 섞인 경우, unknown token과 종료 토큰의 번호가 같은 경우가 들어간다. 종료 토큰 충돌 검사는 가린 위치 뒤의 단어가 문장 벡터에 여전히 영향을 주는지도 확인한다. 두 대조 조건이 가리는 이미지 수, 캡션 수와 토큰 수를 맞추는 검사도 포함했다.

아래는 토큰 치환 도입 전 삭제 방식으로 수행한 기존 검사 기록이다.


2026년 9월 14일에 실제 COCO 자료를 사용하는 소규모 실행과 자동 검사를 수행했다. 전체 COCO 학습이나 전체 규모의 객체 제거 실험은 수행하지 않았다. 이 기록은 코드의 실행 여부를 확인한 것이며 RQ1 가설의 실험 결과가 아니다.

실제 자료 점검은 macOS ARM의 Python 3.11 환경과 Linux ARM의 CPU Docker 컨테이너에서 수행했다. `smoke-real.yaml`로 학습 이미지 4장과 캡션 20개, 검증 이미지 2장과 캡션 10개를 읽었다. 이미지는 식별자 순으로 선택했으며 학습 이미지 식별자는 9, 25, 30, 34이고 검증 이미지 식별자는 139, 285다.

공식 캡션 JSON에서 전체 원본 자료의 이미지·캡션 수도 확인했다. 학습 분할은 이미지 118,287장과 캡션 591,753개, 검증 분할은 이미지 5,000장과 캡션 25,014개였다. 모델 입력에는 소규모 설정에서 선택한 행만 사용했다.

고정된 공개 CLIP ViT-B/32를 실행하고 이미지·텍스트 SAE를 각각 2단계 학습했다. SAE는 각각 64개 특징 중 최대 8개를 활성화하는 소규모 구조였다. 데이터 준비부터 보고서 생성까지 아홉 단계가 종료 상태 0으로 끝났다. 원본 활성값 외에 개념별 이미지 가림 입력 44개와 문장 삭제 입력 50개를 실제 모델로 계산했다. 동일 이미지나 캡션에 서로 다른 개념을 제거한 경우는 각각의 편집 입력으로 센 개수다.

세 그림의 PNG와 PDF, 원본 전체 상관행렬, 원본·편집 활성값, 대표 선택 AUROC, 두 연결 방식의 배정과 판정 결과를 저장했다. PNG 그림의 글자와 축이 잘리지 않는지도 확인했다.

이 소규모 자료에서는 대표 특징의 중복 때문에 두 연결 방식의 평가 행이 모두 판정 불가였다. 세 번째 실험의 검사 가능한 원본 오류는 0개였으며, 결과와 그림에 이를 명시했다. 따라서 실제 COCO 점검으로 연결 회복 효과가 확인된 것은 아니다.

연결 회복 계산은 별도의 인공 활성값 검사로 확인했다. 100행에서 두 객체의 동시 등장 확률을 정하고 잘못된 상관이 큰 상황을 만들었다. 30개 입력에서 조건부 제거를 수행해 표지 상관이 0이 되는지, 두 연결 방식을 실제로 다시 계산하는지, 삭제한 이미지·문장 수가 일치하는지 검사했다. 이 자료는 동작 검사용이며 COCO 측정 결과에 합치지 않았다.

자동 테스트 16개가 통과했다. 검사 범위에는 0 활성값의 동점을 포함한 정확한 AUROC, 상수 특징의 상관 미정의 처리, Greedy의 상대 재사용과 헝가리안의 일대일 제약, 문장 표현 겹침, 학습 자료의 이미지·캡션 행 수 차이, 모델 저장·복원, 입력 내용에 따른 표현 재사용, 중단된 표현 추출과 객체 제거 검사의 재개가 포함된다. `ruff check`도 통과했다.

CPU Docker 이미지를 실제로 빌드했으며 설치된 의존성의 충돌이 없음을 `pip check`로 확인했다. Docker 실행에서는 앞서 내려받은 COCO 자료와 CLIP 가중치를 연결했고, `HF_HUB_OFFLINE=1`로 추가 모델 다운로드 없이 실행했다. 최초 빌드의 의존성 다운로드는 네트워크 시간 초과로 한 차례 실패했으며 다운로드 제한 시간을 늘린 뒤 성공했다.

NVIDIA GPU용 Docker 대상과 전체 COCO 설정은 준비했지만 GPU 서버에서 빌드·실행하지 않았다. 전체 규모의 처리 시간, 메모리 사용량과 학습 성능은 아직 확인하지 않았다. 캡션의 자동 표현 주석도 사람 검토를 완료한 의미 정답이 아니다.

실행의 설정·코드 지문은 각 결과 폴더의 `run.json`, 실제 라이브러리 버전은 `environment.json`, 단계 종료 여부는 `completed` 폴더에 남는다. 기본 Docker 결과 위치는 `/workspace/runs/smoke-real`이며 전체 실험의 결과와 구분한다.

같은 날 서버 실행을 준비하면서 Pyright를 추가하고 전체 공용 코드·실험 코드·검사 코드·보조 스크립트의 타입 오류를 수정했다. Pyright는 오류와 경고가 모두 0개였으며 Ruff 코드 검사와 형식 검사도 통과했다. 새 단위 검사를 포함해 22개 검사가 통과했다. 추가 검사는 재개 후 관측 속도에 따른 예상 시간, 상태 기록 갱신, 실패 상태 보존, 승인 누락과 설정·설명 변경에 따른 실행 거부를 확인한다.

독립 코드 검토에서 미정의 상관의 저장용 0이 연결 최적화에 들어가는 문제와, 제거 조건별로 다른 사례의 점수 평균을 비교하는 문제를 확인했다. 미정의 연결을 최적화에서 제외하고 상수가 된 이미지 대표를 평가 분모에 남겼다. 점수 평균은 두 점수와 세 조건 모두 정의되는 같은 사례·반복으로 비교하고 제외 수를 별도로 기록하도록 수정했다. 두 문제의 반례 검사도 통과했다. 수정된 코드를 독립적으로 다시 읽는 검토에서도 두 문제의 해결을 확인했다.

작은 인공 자료로 아홉 단계와 그림 생성을 다시 실행하고, 완료된 진행 상태가 파일에 남는 것을 확인했다. 이 변경 뒤 실제 COCO 학습을 다시 수행한 것은 아니다. 기존 실제 COCO 소규모 실행과 이후 코드 검사 기록을 구분해야 한다. 전체 실험 설정은 실행 전 승인 기록을 요구하며, 아직 그 승인을 기록하지 않았다.

원격 Linux x86_64 서버의 `/mnt/working/mm-sae`에도 저장소와 Python 3.11.14 환경을 준비했다. Torch 2.6.0+cu124와 CUDA 12.4의 GPU 인식 및 작은 텐서 연산을 확인했다. GPU는 A100의 10GB 분할 장치이며 보고된 메모리는 10,200,547,328바이트다. GPU 환경 확인은 COCO 실험이 아니다.

서버에서 의존성 충돌 검사, Pyright, Ruff 코드·형식 검사와 단위 검사 22개가 통과했다. Matplotlib과 Pyparsing 사이의 폐기 예정 API 경고 14건이 있었으며 검사 실패는 없었다. 인공 자료 설정을 서버에서 CPU로 실행해 아홉 단계와 그림 생성을 확인했다. 전체 실험의 승인 요청은 생성했지만 승인 기록은 만들지 않았다. 서버에서 직접 승인 누락 시 실행 거부를 확인했고, 전체 결과 폴더의 상태는 `not_started`다. 서버 준비 기록은 `/mnt/working/server-readiness.json`에 저장한다.
